## Status vocabulary

Track **lifecycle**, **approval scope** and **artifact role** separately. A superseded revision can remain historically approved; an unapproved proposal can be the current draft. A newer filename does not automatically replace every older scope.

| Dimension | Values and meaning |
|---|---|
| Lifecycle | `CURRENT`: governing baseline for the stated scope; `SUPERSEDED`: replaced by a named later scope; `REJECTED`: explicit engineer rejection; `REFERENCE`: source/supporting or historical alternative, not the governing new design; `UNKNOWN`: insufficient evidence |
| Approval | `APPROVED`: explicit named/specific scope; `NOT APPROVED`: published/reviewed without that approval; `UNKNOWN`: no approval record found; `N/A`: input, source code or illustrative/evidence file is not independently an engineering release |
| Role | `DRAWING`: model-defining PDF; `SOURCE`: editable drawing generator/native input/OpenSCAD source; `CONCEPT`: LLM illustrative PNG; `MODEL VIEW`: actual CAD-model PNG; retained `FUSION VIEW`: actual Fusion PNG; `MODEL/EXPORT`: native/archive/STEP/STL; `EVIDENCE`: review/calculation; `INPUT`: supplied reference |

Drawing approval, model approval, verified exports, print-process acceptance and physical verification are independent. `APPROVED` below never means all of them. Neither a PNG/SVG preview nor an illustrative concept is an engineering drawing or an actual CAD validation view. Preserve existing DRAFT filenames/labels; do not rename them to imply release.

## Filing and revision maintenance

1. Keep exactly one current package per **scope**; supporting current interfaces can coexist with the complete assembly. Identify predecessor/successor and approval evidence explicitly. Never infer acceptance from the newest file date or DRAFT suffix.
2. File every new revision under `schematics/<subsystem>/<revision>/` and `models/<subsystem>/<revision>/`, following the [package and naming rules](../README.md#package-and-naming-rules). Keep one PDF engineering drawing, separate `_concept.png`, editable drawing source and approved model outputs in their respective packages. New OpenSCAD sources/views use `.scad`/`_openscad-view.png`; retain historical `_fusion-view.png` and native archives unchanged. Filing rules do not approve geometry or authorize a Fusion cloud save.
3. Do not sort by mutable `approved/`, `rejected/` or `current/` folders. Use this index and the decision log; no duplicate `latest` PDFs, copied current models or compatibility aliases. Any later authorized relocation must preserve an old-to-new map and original text snapshots, update working links/filesystem inputs, and smoke-run affected generators without overwriting retained PDFs.
4. Preserve the old package when a new drawing/model supersedes it. Do not stamp/rewrite approved PDFs, re-render old sources into new formats, rename legacy SVG/input files or relabel old checks as current. Administrative path-only adaptations retain the original text and provenance; they do not approve the adapted file as a new engineering revision. Update the index and append actual decisions with scope/hash in the log.
5. Unknown approvals stay UNKNOWN. Rejected requires an explicit decision. Unresolved complete assembly/physical approval remains explicit even when a component or nominal drawing is approved.
6. Archived root documents live in [documentation history](history/pre-consolidation/README.md); they are not another source of current TODO/design. The consolidated pages do not alter any geometry, numerical selection or existing approval.
7. The [hierarchy migration record](history/hierarchy-migration/README.md) registers relocated files, frozen originals, legacy metadata and verification evidence. Historical inline execution paths remain time-specific; use the map instead of treating them as live filesystem inputs.
